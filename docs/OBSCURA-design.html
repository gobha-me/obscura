OBSCURA

A seeded deduction roguelike aboard a derelict, in which rendering fidelity is the game state. The ship is drawn as glyph noise until you understand it; understanding it resolves it into art.

PlatformKitty graphics protocol only. No sixel path, no degraded mode, no undo.
StackC++23 (GCC 13+ / Clang 19+), CMake ≥ 3.28, Catch2 v3, no package manager — FetchContent only.
Librarytermforge v0.57.24 consumed as termforge::lib; v0.57.25 is available upstream but is not yet required.
AudioRtAudio, tier 2 (optional). Sink interface is tier 1. See §10.
ImplementerSolo developer with Claude Code. Milestone task files ship alongside this document.
SupersedesOBSCURA design draft v1.

What changed from draft v1 — and since

At rev 2, the v0.1.7 baseline lacked the layer, animation-edit and Kitty keyboard facilities this design needed. That discovery split the plan into a library track (T-series) and a game track (M-series), with an explicit dependency matrix (§13.1). Those original dependencies have since landed, M0 passed, and OBSCURA is now implementing M1 against termforge v0.57.24. The public GitHub tracker is authoritative for live state; stable T-series identifiers here preserve the design intent.

1 · Product definition

1.1 Pillars, stated as constraints

These are load-bearing. A feature that violates one is cut, not negotiated. Each is written so that a reviewer can fail a pull request against it.

#PillarNormative form
P1Fidelity is knowledgeWhether a compartment renders as glyphs or as an image MUST be a pure function of its ResolutionState, which is simulation state. The render layer MUST NOT choose fidelity for aesthetic reasons. If a feature would look identical in a conventional engine, it does not belong.
P2Deterministic to the bitSeed in, world out. Simulation state MUST contain no floating-point, no wall-clock, no unordered iteration. Verified by CI gate, not by intent (§3.5).
P3Consequence, not undoNo save-scum, no un-resolve, no rewind. Spent budget is gone. A resolved compartment stays resolved.
P4Diegetic interfaceNo floating HUD. Every readout is an instrument the player chose to bring. Persistent chrome is limited to the console bezel (§8.2), which is diegetically part of the salvage rig.
P5Fun is the gateM1 proves the loop with one hand-authored case before any generator work begins. Gates are honest or they are worthless.
P6Async community onlyShared daily seed, verifiable replays, leaderboard. No synchronous multiplayer, no voice.

1.2 The loop

PhaseDefinition
PrepareChoose instruments against a shared mass/power budget (§11.4). A loadout is a bet about what kind of incident this is, made under uncertainty.
BoardA derelict is instantiated from the seed. Every compartment is UNKNOWN: box-noise, ASCII garbage, half-legible manifest text. Ignorance rendered literally.
SurveyMove through the hull. Surveying costs charge and promotes a compartment UNKNOWN → SURVEYED: wireframe firms up, damage tint enters the cell backgrounds, evidence markers appear. Not yet art.
GatherExamine evidence. Each item asserts Facts about actors, times, places and actions, and enters the log, which scrolls as real text with inline images.
CommitAssert a triple: this actor was in this compartment doing this thing. Commits are held pending in batches of three.
ResolveThree correct pending commits lock. Their compartments dissolve permanently into full art plates and a partial refund is paid. A wrong batch costs charge and does not reveal which of the three failed.
DebriefRun ends on charge exhaustion or full reconstruction. Score, replay export, unlock progression.

The refund rule is the tension curve. Good deduction extends the run, so a skilled player goes deeper on the same charge; bad deduction ends it. Everything in §4.3 exists to make that curve tunable by one table of integers.

3 · Determinism specification

Non-negotiable. The leaderboard, the replay format and the regression suite all depend on it, and the cheapest place to enforce it is CI.

3.1 Seed and streams

  • Seed is uint64_t. The daily seed is splitmix64(hash(utc_date_yyyymmdd) ^ SALT), computed once at launch and then treated as data.
  • Every subsystem draws from its own named stream: rng(seed, stream_id). Adding a subsystem later must not perturb existing ones, so old replays stay valid across releases.
  • splitmix64 for stream derivation; PCG-XSH-RR for the streams themselves. Both are integer-only and give cheap independent streams.
  • Tile IDs are manifest-declared integers covered by the pack hash, never array indices. If IDs shifted when a tile was added, every existing replay would silently describe a different ship.
  • Weighted selection is integer-only. Tile and variant choice uses cumulative integer weights over a sorted candidate list. The usual entropy-driven formulation of this kind of constraint solving is floating-point, which would violate §3.2 outright.
IDStreamDraws
1STREAM_HULLCompartment count, archetype assignment, graph edges, grid embedding.
2STREAM_CREWActor count, roles, names, initial stations.
3STREAM_INCIDENTArchetype, origin compartment, propagation order, actor decisions.
4STREAM_EVIDENCEDerivation, kinds, instrument gating, veracity assignment.
5STREAM_REDACTRedaction candidate ordering.
6STREAM_FLAVORNon-load-bearing text selection. Never consulted by the solver.
7STREAM_GLYPHGlyph-noise substrate for UNKNOWN compartments. Render-adjacent but seeded, so screenshots of a seed match.

3.2 Numeric discipline

No floating-point anywhere in simulation state. Integers only; where a fraction is unavoidable, Q16.16 fixed-point with explicit rounding. Floats are permitted in the render layer exclusively, and the render layer MUST NOT feed back into simulation — no "measure the animation and branch on it".

3.3 Ordering discipline

No std::unordered_* iteration in any order-sensitive path; sim containers are std::vector or sorted flat maps with explicit comparators. IDs are dense integers assigned in generation order, never pointer- or hash-derived. Sorting is always by a total order that includes the ID as final tiebreak.

3.4 The tick is cosmetic

This is the sharpest correction to draft v1. OBSCURA is turn-based: simulation advances only on discrete input events, never on ticks. App::on_tick(dt) drives the dissolve, cursor blink and log scrolling — nothing that touches sim state. Consequently the replay does not need tick fidelity to reproduce a session, only input order.

The server re-simulates a submitted replay and compares final_state_hash, which makes the leaderboard unfakeable without shipping any anti-cheat. The same file is the bug-report format and the regression fixture: bug reports arrive as playable artifacts. Do not underrate this.

3.5 Enforcement, not intention

GateMechanism
Sim puritytools/lint/sim_purity.sh runs as a CTest test over the [SIM] source set and fails on float, double, std::chrono, random_device, rand(, time(, unordered_, and on any include outside an allow-list. Crude, greppable, effective.
Golden corpustest/corpus/*.replay — at minimum one per authored case plus every bug report ever filed. Each replays and must match its recorded final-state hash.
Cross-configurationThe corpus must produce identical hashes under GCC and Clang, at -O0 and -O2, and under ASan/UBSan. A divergence is undefined behaviour, found cheaply.
Audio independenceThe corpus is run with audio compiled out and with the NullSink; hashes must be unchanged. Prevents audio ever becoming load-bearing.
Stream isolationA test adds a synthetic subsystem stream and asserts the existing corpus still matches — the property that keeps old replays valid across releases.

Transitions are one-way. There is no un-resolving.

4.3 Budget economy

That is the intended shape — the case is solvable, but not without committing before you feel ready.

5 · World model

Declarations are normative; field order is not. All IDs are dense uint16_t indices assigned in generation order.

A commit is verified by scanning the asserting actor's timeline for a step matching (where, what) at any time. Time is deliberately not part of a commit in M1 — asserting when is a candidate difficulty axis for later cases, not a launch requirement.

6 · World generation

Order matters: generate truth first, derive evidence second, redact third. Reversing any two of those produces puzzles that are unfair in ways that are extremely hard to debug.

6.1 Hull topology — a tile grammar

The hull is not a graph that gets drawn; it is a tile layout whose door adjacency is the graph. Inverting that relationship is what makes the layout stage structurally sound rather than validated after the fact: an illegal ship becomes unrepresentable instead of rejected.

Constraints

  • Any tile edge on the grid boundary MUST be hull. Exterior walls stop being a convention the generator remembers.
  • Adjacent sockets must match: door↔door, bulkhead↔bulkhead, open↔open within one compartment. hull never faces an interior.
  • Every compartment MUST carry at least one door. No sealed rooms, ever.
  • The hull graph is derived from door adjacency. Incident propagation therefore runs over real doors, which is more physically honest than propagation over an abstract graph.
  • Selection uses integer cumulative weights over a sorted candidate list, drawn from STREAM_HULL. Backtracking is depth-bounded; exhaustion rejects the seed rather than degrading the ship.
  • Plausibility survives as socket authoring, not as generator logic: the engine room's tile set only offers aft-facing hull edges, airlock tiles require a boundary edge.

Room-label precedence and ship classes

Compartment count is a consequence of ship class, not a die roll. Every class gets the required prefix; larger classes append labels in a fixed order, which is also what gives the renderer's 15-box cap a principled meaning.

ClassRoomsLabels
Required prefix
(every ship)		6bridge · engine room · hold · berth · airlock · galley
Tender6–8prefix, then medbay · comms. Pump-bay function is folded into the engine room at this size.
Freighter — case 001's class10–14prefix + medbay · comms · hold-2 · berth-2 · pump bay · workshop
Liner / hauler16–24the above + second airlock, then repeats of hold and berth to fill

Every ship has an engine room — engineering is a department, not a compartment — so the engine room is in the required prefix and the pump bay is the growth-tier engineering space. This ordering partly closes DR-05: the count follows from the class, and only the class boundaries need tuning against session length.

Embedding still resolves onto the three-band deck plan (§8.1), and the socket rules guarantee what that section previously only asked for: every edge is drawable horizontally within a band or vertically between bands, with no diagonal connectors.

6.2 Ground truth incident

The generator produces a complete causal history before it produces a single piece of evidence: 6–10 crew actors, each with a role and an ordered timeline of (time, compartment, action); one root cause from {hull breach, fire, mutiny, contraband reaction, contagion}; and propagation rules that advance the incident through the hull over discrete steps, moving actors and mutating damage states.

6.3 Evidence derivation and veracity

Each timeline step and each damage transition emits candidate evidence, gated by instrument and kind. Veracity is internal and never surfaced. STALE items were true earlier in the timeline but mislead about the final state; MISLEADING items were planted or misrecorded. Keep MISLEADING at 10–15% of the served set at most — deduction games die when the player stops trusting the fiction. Case 1 ships with zero misleading items and two stale ones (DR-06).

The most valuable evidence is honest but easy to misread: Appendix A's engineer's glove in Hold 2 is TRUE, and it is the item most likely to cost a player a batch. Design for that, not for lies.

6.4 Redaction

After deriving the full set, remove items until the puzzle is solvable but not trivial. "Solvable" must be proven by the solver, never assumed (§13, M3). The redaction pass has one hard invariant: for every commit in the solution key, at least one derivation chain of served items must pin it under the published loadout. Appendix A demonstrates the chain table by hand; M3's solver produces it mechanically.

7 · Rendering architecture

This is the part people write blog posts about, and the part that must be built first: if the resolve transition does not feel good, nothing else matters.

7.1 The five compositing bands

Kitty gives independently addressable image planes interleaved with the terminal's own text and background planes. OBSCURA uses all five. The bottom band is the interesting one: Kitty defines a threshold below which images render beneath cell background colours.

7.3 The glyph substrate

An UNKNOWN compartment is filled from a seeded generator over three character classes: shade blocks (░▒▓) for mass, box-drawing debris (╫╬┼╪) for structure that has not resolved into structure, and half-legible fragments of the real manifest text for that archetype. The third class is what makes it read as ignorance rather than as static — the player can almost read it. Fragment length and corruption ratio scale with distance from the cursor, so the compartment you are standing next to is legibly almost known.

7.4 The resolve transition

The dissolve from SURVEYED to RESOLVED is the signature moment. Budget 400 ms.

Implement it as incremental frame edits to a resident image (T-C1), never as a retransmit. Kitty's animation commands allow editing an existing frame with rectangular blocks and setting per-frame gaps in milliseconds, including gapless frames used purely as composition bases. The dissolve is therefore a sequence of dirty-rect updates to an image already resident in the terminal, which composes directly with termforge's damage tracking: one damage model spanning both text and pixels. That unification is the technical story of the project.

t (ms)StageWhat the player sees
0Plate resident, fully maskedNothing yet. Plate is transmitted once, gapless base frame composed.
0–160Ordered dither reveal, 8 frames of ~20 msThe plate appears through a seeded ordered-dither mask; glyphs are still on top.
160–300Glyph attrition, 4 framesWireframe characters are cleared in reverse structural order — noise first, frame last.
300–400Tint drainCell backgrounds fade to transparent; the plate is the only thing left.

Total wire cost is ~13 dirty-rect edits, not 13 plate transmissions. The dissolve is skippable by keypress — it is a reward, not a cutscene — and skipping jumps to the final composition rather than accelerating the frames.

7.5 The evidence log

The log uses Unicode placeholders: image ID encoded in the cell's foreground colour, U+10EEEE plus row/column diacritics. Salvaged documents therefore scroll as genuine text with inline images, participating in reflow and scrollback. termforge already supports this, tmux-first.

A recovered manifest with the cargo-seal photograph sitting inside the paragraph, scrolling with it, is the screenshot that sells the project. Build it in M1, not M2.

7.6 Art plates: three layers, one resident image

Fixed 4 colours + transparent, 1-bit ordered dither. Aesthetic discipline and payload discipline are the same decision here, and the palette is authored once and checked in as part of the pack manifest.

Art is composed, never enumerated. Baking socket configuration into whole tiles would multiply out to thousands of plates — 8 archetypes × 3 damage states × 16 exterior-edge combinations × door positions × variants. Instead the three lower bands each carry one factor, so the asset count stays additive:

BandCarriesCountNotes
Layer::hullStructural shell: exterior wall, bulkhead and door pieces, per edge kind per orientation~12 piecesReused by every compartment on every ship. Drawn from the tile's socket signature (§6.1).
Layer::plateInterior art, archetype × damage24 platesThe original inventory, unchanged.
Layer::overlayDecals: bloodied, scorched, flooded~8 decalsA bloodied hallway is a hallway plate plus a decal, never a second plate.

Composition happens once, at load, into a single resident image per compartment. This is the load-bearing implementation rule: the dissolve (§7.4) then edits one resident image with dirty rects exactly as specified, T-C1 needs no change, and the bandwidth budget in §7.7 holds unaltered. Compositing at dissolve time instead — three images animating in lockstep — would triple the wire cost of the signature moment and is explicitly not the design.

7.7 Bandwidth budget

A session must stay playable over ssh. This is a design constraint from day one, not an optimisation pass, and it needs a meter (T-H4) to be real.

7.8 Image lifecycle

Per spec, clear-screen and main↔alt-screen transitions must clear images. Get placement and deletion lifecycle correct in M0 or you will chase ghost images for a month: write the lifecycle tests before the game logic exists (T-D1). Minimum coverage — clear-screen mid-dissolve, alt-screen leave/return with plates resident, SIGWINCH mid-dissolve, quota exhaustion with an eviction while a dissolve is in flight, and process death mid-transmission.

Gesture rules. Repeat events inside AIM never advance a field more than one step per event. If the terminal stops reporting release events mid-session, the session pauses to a modal and refuses to continue: a silent downgrade here would let a player commit by accident, which violates P3 in the worst possible way.

10 · Audio

10.1 Tier ruling

You asked whether audio is tier 1 or tier 2. The answer follows from the loop: OBSCURA is turn-based, every state change is legible in the render bands, and nothing is time-critical. Audio therefore carries atmosphere and confirmation, never information.

Ruling. The sink interface is tier 1 and lands in M1 with a NullSink, so call sites exist and are exercised from the beginning. The RtAudio implementation is tier 2 and lands in M2 behind a CMake option. No mechanical fact may be conveyed by audio alone, and CI proves it by running the replay corpus with audio compiled out and asserting identical state hashes (§3.5).

This is a deliberate trade: the DOS-era austerity that makes the game feel like an instrument also means it reads correctly in silence, over ssh, in a shared office. Atmosphere is a large upside — a low hull drone under the survey loop and a single dry mechanical report on a locked batch will carry more dread than any sting — but it is upside, not foundation.

10.2 Where RtAudio can live

termforge's dependency policy is stdlib-only at runtime — no third-party deps in the shipped library. RtAudio is a third-party dependency, so it cannot go into termforge::lib without breaking that policy, and that policy is one of the library's better decisions. The split:

ComponentHomeRationale
AudioSink interface + NullSinkOBSCURA src/audio/ (T-G1)Application-owned, pure virtual, stdlib-only and zero-dependency. The optional mixer remains separate.
RtAudioSinkSeparate optional OBSCURA target (T-G2, unfiled)M2 work only after a concrete call site exists. TermForge's stdlib-only policy remains untouched.
Process-boundary sink (paplay/pw-play)Optional adapter (T-G3, unfiled)A possible zero-dependency reference, not a commitment before M2.

OBSCURA already owns the sink interface and null implementation. The eventual backend may live in a separate optional target or under OBSCURA's audio layer; that M2 choice must not add a third-party dependency to termforge's shipped library.

Everything generated offline. Nothing generated at runtime. The runtime is a pure deterministic C++ program with all generative work confined to offline content production.

Baked into a versioned pack with a manifest hash. The manifest declares each entry's stable integer ID and its socket signature and weight; both are covered by the hash, so a replay can never be reinterpreted against shifted tile IDs. 12 · termforge work plan

Grouped as epics; each ticket is small enough to land in one sitting with a test. Live status and issue mappings are maintained in the public GitHub tracker and 05-termforge-tickets.md.

The implementer files these

The agent is authorised to open feature-request tickets against termforge directly. It should file the T-series itself rather than waiting on a human, following the protocol in §12.1 — search before filing, one ticket per unit of work, acceptance criteria that a test can satisfy. Filing a ticket is not the same as landing it: library implementation belongs in a dedicated termforge session, on its own branch, under termforge's conventions and both-compiler verification.

12.1 Ticket-filing protocol

  1. Deduplicate first. Search current GitHub issues for the facility, not the ticket name. The T-series mapping in the live handoff identifies older requests that landed under different titles; do not infer state from the historical issue numbers in this specification.
  2. One ticket, one landable change. If a ticket cannot be described by a single acceptance sentence with a test behind it, split it.
  3. Body shape — four short sections, no more: Motivation (what an application cannot do today, with the concrete call site), Proposed API (signatures, not prose), Acceptance (the assertion a test will make), Notes (protocol references, affected drivers, whether it is an API break).
  4. Respect the library's rules in the proposal itself. No third-party dependency in the shipped library; degradation is an event, never a silent downgrade; drivers emit bytes verbatim and sanitisation stays in the renderer; capability requirements are pinned, never emulator versions. A ticket that violates one of these will be closed, correctly.
  5. GitHub is the work record. The public issue is the canonical request body, discussion and state. Keep the stable T-series identifier in the design so intent does not depend on an issue number; do not maintain a second body copy (DR-10).
  6. Label enhancement for new facilities, and reference the milestone it blocks (M0–M4) in the body, not in the title.
  7. Attribution. Agent-authored commits carry the model trailer termforge's conventions require. The same honesty applies to tickets: say that the request comes from the OBSCURA flagship work.
  8. Do not file speculative tickets. If OBSCURA can be built without it, it is not a ticket yet. Optional facilities are filed only when an active milestone supplies a concrete call site.

13.3 Test strategy

termforge's philosophy applies unchanged: test how code fails, not just the happy path. For OBSCURA the failures that matter are a dissolve interrupted by a resize, a batch resolved with a full log and an empty one, a replay recorded on one build and verified on another, and an evidence set whose redaction removed the only chain to a commit.

15 · Non-goals

Written down so they do not get helpfully added later.

  • No real-time combat and no tactical layer. The tension is epistemic, not kinetic.
  • No synchronous multiplayer, no voice. Async daily seed only — a community-design choice, not a technical limitation.
  • No sixel fallback. Kitty only.
  • No LLM at runtime. Content generation is offline and checked in.
  • No mouse-required interaction.
  • No complex script or text shaping. termforge does not do it and the game does not need it.
  • No un-resolve, no undo, no save scumming. One seed, one run.
  • No audio-only information. New in rev 2, and load-bearing for §10.
  • No runtime asset generation and no runtime dithering.

Surveying all nine costs 72 SC, movement about 16 SC, and reading all sixteen items 48 SC — 136 SC against a starting 120. One correct batch (+15) makes it reachable; two make it comfortable. The case therefore requires committing before the player feels ready, which is the intended pressure. Tune here first if M1 playtests feel either cruel or slack.
